Renaming an account keeps a running session's Remote Control working, and artifact publishes no longer fail when the remote and serving accounts are in different orgs.

## Fixed

- **A rename broke Remote Control in a running session.** chottag remembers, per Claude Code session, which account answered its `POST /api/oauth/validate`, so Remote Control keeps the account it pinned at start. The memory held the account's name, so after `chottag rename` the old name no longer matched, the validate went out as the serving account, and Remote Control stopped whenever that was another login. The memory now also records the account's slot directory, which a rename never changes, and follows it. A session recorded by an earlier version follows the rename by email when only one account has it; with two accounts on one email it is not guessed, and the validate goes out as the serving account as before. The warm loop also keeps the renamed account fresh for its sessions. Nothing to do: the entry updates at the session's next validate.
- **An artifact publish was denied: "caller org does not match owner org".** Claude Code's Artifact tool publishes in two steps: `POST /api/frame/deploy/prepare`, which chottag sends as the remote account, then a call to its own server at `/api/artifacts/mcp`, which chottag did not know and sent as the serving account. With the two accounts in different orgs, the server refused the publish. Everything under `/api/artifacts/` now goes to the remote account, and so does `/v1/pages/` (Claude Pages and Claude Docs), whose objects also belong to the remote account's org.
- **Archiving a Remote Control environment, and creating a webhook routine, went out as the serving account.** `POST /v1/environments/{id}/archive` now follows the environment's owner, and `/v1/code/webhook-triggers` goes to the remote account like the other routine routes.
- **A `chottag: route drift` notice after a switch to an account in another org.** Claude Code's background API-credit offer check (`/api/oauth/organizations/{id}/quirky-lollipop/link-offer`) names the session's own org, so another org's account gets 404. It now stays on the session's own login, like the marketplace and model-selector checks.

## Added

- **A refused new route is named.** A request on a route chottag's table does not list that is sent as the serving account and answered 403 (or 401 `permission_error`) usually belongs to the remote account's org. It was already counted as route drift; now the daemon log has one line per method and path an hour, `chottag: GET /api/x/{id} was refused as work (403); it may belong to the remote account; please report it`, with the templated path (never an id, a query or a body), and a desktop notice comes with it. `chottag doctor`'s `route-drift` row says how many of the count were of this kind, and `status --json` shows `daemon.routeDriftUnclassified` when it is not 0. Routes the table lists behave as before.
