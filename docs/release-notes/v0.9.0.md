The chottag plugin gains a mod for Claude Code 2.1.287 or newer: a status card above the prompt, notices, `/ct` commands and a `/login` guard. `chottag statusline` shows the time left to the next reset. And a token that goes stale now either renews or says why: the daemon logs every refresh, and `token: stale` clears when the token renews.

## Added

- **The status card.** Above the prompt, flowing in two rows from 100 columns, three from 60, one line below, with a blue bar on its left: the serving account and the remote account (one row, `Serving + remote`, when they are the same; `This session` with `pool serves` when `spread` placed the session elsewhere), both usage windows with a bar, a percent and their own reset in local time (`in 42m`, `in 3h 20m (01:40)`, `Mon 18:00`, `Oct 9, 18:00`), the window closer to its switch point in bold, and `N of M accounts ready`. An older chottag (before 0.9.0) shows no remote segment. `NO_COLOR` turns colour off.
- **Notices.** A toast when the session's account changes (`chottag: now on C (was B: limit)`), when an update is available (once per version per machine), and when the remote account needs a login or its token stays stale (at most once an hour). A connector call that comes back refused gets one line saying which account it went out as.
- **`/ct`.** `/ct status`, `/ct next`, `/ct tag NAME`, `/ct pool` and `/ct help` run chottag from the prompt without asking Claude. `/chottag` stays the skill's.
- **A `/login` guard.** In a chottag session `/login` and `/logout` are stopped with a message that says what to do instead, because there they change Claude Code's own (Home) login.
- `chottag statusline --json` has `limited`, `lastSwitch`, `remote`, `remoteToken`, `fiveHourResetsAt`, `sevenDayResetsAt` and `nearWindow`, which the card reads.

## Changed

- `chottag statusline`'s `↻` now shows the time left, in local time: `↻ 42m`, `↻ 3h20m`, `↻ Mon 18:00`, `↻ Oct 9 18:00` (it was a clock time, `↻ 19:00`). The cmux pill follows.

## Notes

- The mod only adds visibility and the guard. The shim and the proxy still decide each request's account, and an older Claude Code ignores the mod. It does not run in `claude -p`, the VS Code chat or cloud sessions.
- It talks to chottag only through the CLI, and never reads `~/.chottag`, a slot or a token. If your own `statusLine` also runs `chottag statusline`, both show; drop either.
- To change Home's login anyway, start a session with `CHOTTAG_BYPASS=1 claude`, or run `claude auth login` in a terminal.

## Fixed: stale tokens

- `token: stale` on `chottag status` no longer sticks. It clears when the token renews, and when a request goes out as that account again; before, only a passthrough ever changed it.
- The token refresh runs the slot's own `claude` without the daemon's auth and session variables (`CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_SESSION_KIND`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`), so a daemon started from a shell that has them set can no longer make the refresh renew nothing. Everything else, and the slot's `CLAUDE_CONFIG_DIR`, is unchanged.

## Added: token refresh

- `chottag daemon logs` has one line per refresh outcome: `refresh C: renewed, expires in 7h59m (request, 5.2s)`, `refresh C: claude exited 0 but the token is still expired; retry in 2m`, `refresh C: failed: <reason>`. The same line repeats at most every 10 minutes; a different outcome always logs. A line names the account, the outcome, the time and the expiry, never a token.
- A refresh that exits 0 at least three times in a row, over at least 10 minutes, without renewing the token makes the account `needs-login` (reason `refresh-not-renewing`). The log says `chottag: refresh C: claude exited 0 but the token is still expired; retry in 15m` and then, with the real number of tries and minutes, `chottag: refresh C: still expired after 6 tries over 16m; it needs a login (run: chottag login C)`, and you get a notice that says `chottag login C`. One renewal, a failed attempt or a re-login resets the count, and the daemon probes a locked-out account once every 15 minutes, whatever its role: a renewal lifts the lockout without a login.
- The daemon keeps each pool's serving account's token fresh too (6 minutes or less left), not only the remote account's, and runs a warm pass about 10 seconds after it logs `woke from sleep`. Fewer prompts after an expiry or a wake go out on Home's own login: one sent in those 10 seconds, or before the refresh ends, still does, and only each pool's serving and remote account is warmed (not other rotating members or pinned accounts). A refresh that left the token as it was because it is not yet due logs `chottag: refresh C: token unchanged, not yet due (warm, 1.2s)`.

## Changed: token refresh

- A Keychain that is locked or has no UI right after a wake is retried every 30 seconds for the first 5 minutes, then with the usual backoff (up to 15 minutes).

## If an account keeps going stale

Run `chottag daemon logs`, look for the account's `refresh` lines, and see [Troubleshooting](../troubleshooting.md). Where the refresh renews nothing three times, run `chottag login <name>`.
