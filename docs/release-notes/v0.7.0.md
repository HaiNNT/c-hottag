The `spread` policy: sessions spread over your accounts, each kept on one account so its prompt cache stays warm. The plugin skill, the agent guide and the README also now cover everything 0.6.0 added.

## Changed

- When `chottag update` defers the daemon restart and the running daemon can't restart itself (it predates 0.6.0, auto-restart is off, or it is newer than what was installed), it now says so plainly, `the running daemon (0.5.0) can't restart itself: run chottag daemon restart once when convenient`, and `update --json` has `selfRestart`. The plugin skill tells Claude Code to run `chottag daemon restart` to finish the update.
- The plugin skill documents `update_in_progress`, `statusline --json`'s `updateAvailable` and `restartPending`, the ` · ↑<v>` and ` · ⟳<v>` status-line markers, `CHOTTAG_NO_UPDATE_CHECK=1`, `own` and `adopt`.
- `docs/for-claude-code.md` tells an agent about the daily update check and `update_in_progress`.
- The README's feature list mentions the update check and the idle restart.
- A test now fails when a command or flag in the usage text is missing from the skill or `docs/commands.md`.

## Added

- `chottag policy [serial|spread]` sets how new sessions are placed: `spread` puts each new session on the account with most headroom and keeps it there (`policy` and `pin` in state.json; `bad_policy` for any other value).
- Under `spread` a session is placed on its first request and stays on that account: it moves only when its account reaches a switch point or is limited, or when its prompt cache is already cold and a move clearly helps, and never twice within 10 minutes. Accounts with rotation off never get a session. Placements are kept in `run/placements.json`, so a daemon restart or an update leaves sessions where they were; a notification says when sessions moved.
- `chottag status` shows a `policy: spread` line (with `pin: NAME`) under spread, and `policy` and `pin` in `--json`; under `serial` nothing changes.
- Under `spread`, `chottag tag NAME` also pins new sessions to NAME, `chottag tag --unpin` clears the pin, and `chottag next` is refused with `spread_next`.

- A top-level or per-account `state.json` key this chottag does not know (one a newer release wrote) is now kept and written back unchanged, so an older chottag can no longer erase a newer one's fields. (Keys inside the `auto`, `updates` and `trace` settings are not covered yet.)
- `chottag policy spread` and `tag NAME` under spread warn (`daemon_predates_spread`) when the running daemon is older than the binary: restart it first with `chottag daemon restart`, or it ignores the policy and may reset it. Do that after every update, before turning spread on.
- Turning spread on leaves a running session on the account it is using when that account can take it. Under spread, `serving` is set on the daemon's roster tick (never on a response) and only moves when another account is clearly better.
- Rolling back below 0.7.0 (`chottag update --version v0.6.x`) returns to serial behaviour and forgets the placements; run `chottag policy spread` again after upgrading back.

## Fixed

- `chottag update`, `setup` and `adopt` no longer clear a real needs-login. Adopt re-stamped every registered account's `loggedInAt` on each run, so a broken login looked fixed after an update. Now only `chottag login`, or adopt finding a changed email or org in the slot, advances it. After a `/login` inside a slot with the same account, run `chottag login` (or let the daemon's next good token clear it).
- The daemon's restart-when-idle state in `run/restart.json` is no longer deleted by `chottag status` or the daemon itself. The session registry treated every `*.json` in `run/` as a session entry and removed the ones without a pid, so the once-per-version notices and the hourly attempt limit were lost; it now reads only the `<pid>.json` entries it writes.
