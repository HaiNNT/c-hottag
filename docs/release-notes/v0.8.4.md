`chottag login` and the daemon's token refresh now run the real Claude Code, never chottag's own shim, so an account can no longer record another account's email.

## Fixed

- `chottag login`, `logout`, `adopt` and `setup` (through `adopt`) resolve the real `claude` from PATH, skipping chottag's own `bin/`, when you give no `--claude`. Before, a bare `claude` found the shim first once `chottag setup` had put `~/.chottag/bin` first on PATH, and the new slot recorded the serving account's email. Since 0.8.3 the shim already skipped chottag for `claude auth ...`, so a login through it was right from 0.8.3; this removes the dependence on that. `--claude PATH` is still used as given. Reported in [#2](https://github.com/HaiNNT/c-hottag/issues/2).
- The daemon's background token refresh (`claude mcp list` in a slot) did the same through the shim, and could write the serving account's email into another account's slot while leaving its organisation right. It now runs the cached real `claude` (or the one on PATH), looked up again on every refresh, and every `claude` chottag runs in a slot (login, logout, the identity read and the refresh) carries `CHOTTAG_BYPASS=1`, so one that still reaches the shim runs the real binary with no proxy.

## Added

- `chottag adopt` (and `setup`, `chottag update`) no longer copies another registered account's email into an account when its email would move onto a serving account's and the organisation stays (the corruption's signature; a blank stored organisation counts as staying). It keeps the stored email and organisation, does not stamp the account as logged in, lists the slot under `skipped` with the reason `identity_suspect`, and warns `identity_suspect`. Accounts that share an email legitimately (one login in several orgs), an account healing back to its true email, and a first fill of a blank email are adopted as before.
- `chottag doctor` has a new row, `identities`, which lists accounts that share an email as `info`. It never fails doctor: sharing is expected when one login is in several orgs.

## If several accounts show one email

Before 0.8.4 the background refresh could write the serving account's email into another account's slot. To repair: upgrade (`chottag update`), run `chottag daemon restart`, then `chottag login <name>` for the accounts that are wrong only. Several accounts may share an email when one login is in several orgs.
